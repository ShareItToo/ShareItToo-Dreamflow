## Reconciliation flow

1. The server starts one immediate run and one bounded interval timer. An
   in-process promise guard prevents overlapping runs in the same process.
2. A transaction selects at most the configured batch size of active non-live
   cases using `FOR UPDATE SKIP LOCKED`.
3. Each exact P0-without-owner or overdue-next-update condition attempts one
   append-only internal support event with a condition-bound idempotency key.
4. The transaction records aggregate success state. A failed run records only
   a sanitized stable error code and rethrows so the next interval may retry.
5. Health/readiness queries both worker freshness and unresolved database
   conditions. Missing state, staleness, a last error or an unresolved
   condition returns `degraded`.
6. An elevated admin may read a minimized active queue. A resolved case,
   assigned P0 or changed next-update deadline no longer appears as active;
   historical events remain immutable.

The interval is bounded between 30 seconds and 15 minutes. Maximum health
staleness is at least three worker intervals. The timer is unreferenced and is
cleared during normal server shutdown.

## Message correction boundary

S3I templates whose exact placeholder contract includes
`next_update_date`, `next_update_time` or `next_update_datetime` require a
future server deadline at draft creation. Publication reloads and locks the
case, then repeats the same test immediately before recording `sent`. A stale
draft therefore cannot publish an already-false promise.

The watchdog itself does not edit or publish a correction. It exposes the
condition for an authorized human workflow, preserving the catalog's review
and immutable correction-chain rules.

## Database, privacy and audit

Migration `039` adds a content-free singleton worker-state table and a partial
index for the two operational event types. Alert payloads contain only case
control state and `externalNotificationSent=false`; no summary, rendered
message, evidence or reporter data is copied.

The admin response returns only identifiers, case number, alert type, status,
priority, current owner reference/role and timestamps. It is protected by
authentication, active-account, admin-role and Staff-Step-up middleware and by
`private, no-store` caching.

Privacy and retention manifests bind the new sources and remain `draft` with
approval and destructive execution blocked. Rollback refuses to remove the
watchdog schema after durable operational alerts exist.

## Explicit exclusions

- no email, push, SMS, webhook, Telegram or provider adapter;
- no owner assignment, automatic deadline rewrite, escalation or closure;
- no user-facing promise generated by the scheduler;
- no incident-wide authority, staffing claim or SLA guarantee;
- no production, Cloud, VPS, DNS, payment, Store or real-money mutation.
