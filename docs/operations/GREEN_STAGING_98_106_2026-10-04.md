## Interface and hard boundary

Entry point: `node tool/validate_green_staging_98_106_runtime.mjs`.
Pass all four `--binding`, `--publication`, `--target`, `--config` protected
paths and their corresponding `--NAME-sha256` exact-byte hashes. Never put
secrets or protected JSON bodies on the command line.

`--mode plan` is the default; `--mode validate` verifies bindings without a
Docker call. Explicit `--mode preflight` reads Docker and the source ledger.
Generic `execute` is rejected. Mutation requires either `rehearse` or `promote`
and the distinct complete consent/input set below. No invocation in this
document constitutes consent to execute it.

`--mode collect` takes the protected publication path/hash, externally supplied
`--ops-commit`, an existing `--evidence-directory` (owner 0700, outside checkout),
and `--acceptance-mfa-file`. The collector validates committed source/manifest
bytes, reads only Docker, then exclusively writes `collected.target.json`,
`collected.config.json` and `collected.private-runtime.json` (owner 0600).
It prints artifact names, exact-byte hashes and canonical-content hashes only.
The private-runtime artifact contains protected configuration and must never
be copied into Git/logs. A collision fails before collection. Collection is
**not authorization**: independently review target/config content hashes and
supply them in the external binding; the collector does not generate approval.

For `rehearse`, also supply `--private-runtime` and its exact-byte
`--private-runtime-sha256`, `--evidence-directory`, and exact confirmation:
`--confirm rehearse:RUNTIME_COMMIT:OPS_COMMIT:TARGET_CONTENT_SHA256`.
All uppercase placeholders must be replaced by independently validated values.

For `promote`, all of those protected inputs remain required, plus the
successful `--rehearsal` and its `--rehearsal-sha256`, exact protected `--backup`
path, and a **different** confirmation:
`--confirm promote:RUNTIME_COMMIT:OPS_COMMIT:REHEARSAL_BYTE_SHA256`.
The receipt must be at most one hour old, not future-dated, have complete
acceptance/cleanup proof, and match publication/Ops/target/config/material
bindings. The original target snapshot stays immutable; the exact source ID
must now be stopped under the versioned seal name, not recollected as a new ID.

The 31-command production-shaped prefix reads API/database, all 21 witnesses,
both networks and foreign membership, uploads, exact immutable image/OCI
revision, source ledger and PG major, then rechecks API/database identities.
Its only success is `read_only_prefix_passed` with
`boundary=before_stop_seal_or_write`, `mutationAdapterImplemented=true`,
`rehearsalPassed=false`, `promotionAuthorized=false`,
`publicReleaseComplete=false`. Concurrent changes after that prefix are not
covered; it is not a later write authorization.

## Implemented mutation sequence and hard recovery boundary

Stabilize source changes through Sol review before binding final execution
evidence. `reviewedImplementationCommit` and `opsCommit` remain external inputs:
the reviewed source blobs must equal current Ops/worktree blobs, runtime690
must be their ancestor, and the manifest bytes must equal the Ops Git blob.
Thus no self-hash cycle is introduced. A later unrelated Ops commit is allowed
only if all bound implementation blobs are unchanged.

The adapter implements these gates; local tests are not their live receipts:

1. Fresh target/source/config/material/tool/user-readability and evidence-family
   checks; exact IDs and complete writer inventory before stop/seal. No guessed
   UID/GID, configuration path, port or network assumption.
2. Stop/seal captured API identity; prove all writers quiescent before and
   after backup. Exclusively create owner-only custom-format dump, hold stable
   descriptor, hash verified bytes; never restore a later path substitute.
3. Create/inspect/start owned isolated PG16 from the pinned image; verify
   identity, internal network, official initialization-complete marker and two
   successful SELECT 1 probes before restore. Verify restored ledger98 and all
   old business fingerprints before migration.
4. Run the exact immutable 690 runtime's migrations 099–106. Verify exact106
   ledger, expected new tables/constraints/functions, zero rows in all 28 new
   namespaces and unchanged old business fingerprints. Run again and verify
   idempotence including migration timestamps. Compare actual readiness finding
   identities/causes/status/time classes, not only counters.
5. Candidate acceptance must use isolated DB/uploads and verified namespace
   connectivity. An internal Docker network does not imply that host-published
   ports are reachable. No provider egress, public route or canonical fixture
   writes. Require exact runtime/Ops controlled-acceptance evidence.
6. Cleanup only captured owned resource IDs, including anonymous volumes with
   their owned containers. No name-only/foreign deletion. A cleanup failure
   overrides PASS, including create-response-loss paths.
7. Require fresh successful rehearsal/acceptance/backup and separate explicit
   canonical confirmation. Recheck all identities and configuration at the
   canonical boundary. Once canonical migration begins, **never** automatically
   restart the old image, run down migrations or restore over canonical data.
   Failure means isolation plus reviewed forward recovery; backup restoration
   needs a separately authorized recovery path.

Source MFA/Firebase files must remain root-owned, single-link regular 0640
files with unchanged held-descriptor metadata and bytes. Isolated acceptance
requires a separately provisioned root:65532 0640 copy of the **same MFA key**;
the runner never creates, chmods, rotates or weakens protected material. A
network-none worker in the immutable runtime verifies actual non-root UID/GID
and reads all three mounts before the source is stopped. Missing material,
image availability, Docker access or exact bindings is a hard failure, never
an install/pull/permission-change fallback.

Rehearsal leaves the source stopped and sealed even on failure: it never
automatically restarts an old image. It uses an owned internal network,
anonymous owned DB/uploads volumes, dedicated free loopback port 18082 and
exec-in-container HTTP probes, not host reachability assumptions. Provider
credentials are absent and Firebase/access gate are off only in the disposable
candidate; original protected configuration is preserved for canonical startup.
Public staging must return 502/503 while quiesced; transport failure is not
accepted as proof of isolation. MFA/identity synthetic writes happen only in
the isolated restored DB. Cleanup removes exact owned IDs and their anonymous
volumes atomically; it never issues standalone volume removal.

Promotion independently rechecks sealed source, DB IP/network identity,
no-writer state, backup bytes, complete source fingerprints, material and all
external bindings. It writes an exclusive canonical-started boundary receipt
before starting the first canonical migration worker. From that point, even
response loss means forward recovery only. The successor starts on the
internal network with original provider-off semantics; provider-egress network
attachment/public routing is last, after exact runtime/readiness/data checks.
Failures isolate the exact new ID (stop and detach egress), retain it for
reviewed forward recovery, never restart the predecessor or down/restore the
canonical DB. Create/stop/rename/start/network/remove response loss is accepted
only after exact identity/postcondition readback. Cleanup/isolation failure
overrides success. A promotion receipt does not claim frontend/provider or
public pilot release completion.
